# BattleText Forever — developer notes

Scrolling combat text for **World of Warcraft: Forever** (interface 16001, client 1.60.x): your hits, heals and misses, the damage you take, and notifications.

- Author: `severd8`. License: MIT.
- CurseForge project ID: `1722502` (in the `.toc` as `X-Curse-Project-ID`).
- Sister addons: TauntMaster Forever, ToppedOff Forever, Outfitter Forever. This project's setup mirrors ToppedOff's.
- Written from scratch. It's in the spirit of MikScrollingBattleText, but uses none of its code (MSBT is All Rights Reserved, and its combat log parser can't work on Forever).

## Files

- `BattleTextForever.toc` — `## Version: @project-version@` is filled in by the packager from the git tag. `BattleTextForeverDB` holds the settings every character shares; `BattleTextForeverCharDB` (per character) holds `own` and, when it's on, that character's own `settings` (a copy made by `SetOwnSettings`). `BT.db` is whichever is in use, chosen on `ADDON_LOADED`; both are brought up to date the same way (`MoveOldSettings`, `FillDefaults`).
- `Parse.lua` — turns one Combat Log line into a table (`ns.Parser:Parse(line)`). Its only game calls are reading the game's text and your own GUID.
- `Core.lua` — settings, the four scroll areas and their animation (`Emit`, `Animate`), turning `UNIT_COMBAT` and parsed lines into text (`OnUnitCombat`, `OnUnitHit`, `ShowCombat`), notifications, the Start button, minimap button, slash commands, events.
- `Theme.lua` — **the shared look, and the same file in TauntMaster Forever, ToppedOff Forever, Outfitter Forever and BattleText Forever.** Change it in one repo, then copy it to the other three. It finds the addon's name and logo from the folder name (`BRANDS`). Loaded first. Don't use Blizzard templates (UIPanelButtonTemplate, UICheckButtonTemplate, WowStyle1DropdownTemplate...) in a window with this look.
- `Options.lua` — the options window, built with `Theme.Window`: tabs down the left (`TABS`, also `BT.CONFIG_TABS`), each page one or two `Card`s of switches (the Spells tab: an edit box and a list of rows, `BuildSpells`) (`Setting`), sliders and dropdowns (`T.Dropdown`; the font list sets `menuScroll` so it scrolls). The window keeps `fontDropdown`, `outlineDropdown` and `critOutlineDropdown` for the tests. Closing it locks the text areas. `/btf copy`'s window is in the same look (`T.ScrollArea` round an edit box).
- On screen: the text areas' boxes (shown while unlocked) are `T.Panel` with a `T.HeaderStrip` along the top; the Start button is a `T.HeaderStrip` itself (logo, "Start BattleText"). Chat lines start with `T.CHAT_PREFIX`.
- Colors: `BT.DEFAULT_COLORS` are the starting ones, `db.colors[key]` the ones changed (`SetColor`); `ApplyColors` writes them into `BT.TEXT_COLORS` in place, on load and in `ApplySettings`. School colors for spells aren't in the list.
- Each area has `prefix` in `BT.AREAS` (`out`, `in`, `heal`, `n`), and its own `<prefix>Size` (percent of the text size, in `Emit`) and `<prefix>Alpha` (percent, in `Animate`) (`AreaSetting`).
- `db.shortNumbers`: `Commas` writes 10,000 and up as 12.3k / 1.2m.
- `db.healWho`: a heal of yours read from `UNIT_COMBAT` on another unit gets the unit's name (`HealedName`), only if `UnitName` is readable (the game can hide it: `SecretWhenUnitNameIdentityRestricted`). Names in the combat log lines are scrambled and never used.
- `/btf check` (`CheckGameData`): `C_Spell.GetSpellName` for every ID in `PERIODIC_SPELLS`, `SHIELD_SPELLS`, `SEAL_SPELLS`, `SELF_BUFFS`, `FLIGHT_SPELLS`, `REACTIVE_SPELLS`, `INTERRUPT_SPELLS` and `SKILL_SPELLS` (on an English client the name must match), `SKILL_RANK_UP`, and `GetFileIDFromPath` for the logo and tab icons. The report goes into the debug record, so `/btf copy` shows it. Works on any character: the game knows every spell, not only your class's.
- Seals (paladins): `SEAL_SPELLS`, `JUDGEMENT`, `SEAL_TIME` (30, Classic's). `self.seal` is the seal on you: set from your cast (`OnSpellcast` -> `SetSeal`), from your buffs out of a fight (`ScanShield` -> `SeenSeal`; the first reading after login is quiet), and cleared by another seal, its time running out (`C_Timer.After`), or a reading without it (`LoseSeal`). **Judgement leaves the seal on** (1.11.1, issue #7: on Forever it doesn't use it up; Classic's rule made "-Seal" show at Judgement and a "+Seal" at the next buff reading). A buff reading gives the seal's `expirationTime` (its `ends`) and `duration`, kept in `db.sealTimes[name]` (`SealTime`, else `SEAL_TIME`) for the next cast in a fight. `db.nSeals` shows "+Seal"/"-Seal" in Notifications (`TEXT_COLORS.seal`). In `ResolveFrame`, a hit that's nothing else, of the seal's damage school (Holy), on the same unit as a physical hit in the same frame, is the seal's (`SealFor`), unless `db.outSeals` is off. **1.16.2 (a player's report: SoR hits showed as plain numbers): the seal's hit comes with its log line, while the swing's `UNIT_COMBAT` trails its line by up to ~1s, so the seal's is usually ahead of the swing. `SealFor` also takes a physical hit of yours on that unit up to `SEAL_AFTER_SWING` (0.5s) before (`self.struck`; not for the Hammer of Wrath veto, `frameOnly`). A hit `SealOn` fits that nothing named waits (`WaitForSwing`, `self.sealWait`) up to `SEAL_SWING_TIME` (1.2s): your physical hit on the same key (`SwingLanded`, beside `self.struck`) shows it as the seal's; else it's shown unnamed when the time's up. **Not yet seen in game**: that order and timing on Forever, and whether `expirationTime`/`duration` are readable on a seal out of a fight.
- Buffs (`db.nBuffs`, off by default): every reading of your buffs (`ScanShield`, also on `PLAYER_REGEN_ENABLED`) goes to `SeenBuffs`, which compares it with the last one and shows what came and went. A reading in a fight fails (hidden), so the first one after it shows the fight's changes. Left out: seals, `QUIET_BUFFS` (food and drink, English names), buffs with `duration` 0, and everything while `UnitIsDeadOrGhost`. In a fight the buffs can't be read (`UNIT_AURA` and the aura functions are secret then, `SecretWhenAurasRestricted`), but your casts can: a cast of a buff on you only (`IsSelfBuffCast`: `C_Spell.IsSelfBuff`, else `SELF_BUFFS`, else `db.learnedBuffs`, names seen turning up out of a fight within 3s of your cast of that name) shows "+" at once and goes in `self.fightBuffs`; the first reading after the fight skips their "+" and shows "-" for those gone.
- Ability alerts (1.11.0, `db.nAlerts`, `REACTIVE_SPELLS`: ID, English name, class, what opens it, level trained or none for a talent). `React(what)` shows "<name>!" in Notifications (`TEXT_COLORS.alert`, `crit` so it stands out), once per `REACT_GAP` (1s) each, if `HasReactive`: the class (`UnitClass`'s second answer), the level for a trained ability (ranks make `IsPlayerSpell` on the first rank unreliable), `IsPlayerSpell`/`IsSpellKnown` for a talent. "dodged": a target miss of action or flag DODGE in `ResolveFrame` that's yours (`claimed`), or a readable miss line of yours (`ShowCombat`). "avoided"/"parried": `UNIT_COMBAT player` DODGE, PARRY, BLOCK, or a WOUND flagged BLOCK/BLOCK_REDUCED, checked before any setting returns. Target health is secret, so Execute and Hammer of Wrath go by the game's own answer (below).
- "Usable" alerts (1.13.0, `REACTIVE_SPELLS` entries with `"usable"`: Execute, Hammer of Wrath). `CheckUsable(newTarget)` on `SPELL_UPDATE_USABLE`, `UNIT_HEALTH` (target) and `PLAYER_TARGET_CHANGED` asks `C_Spell.IsSpellUsable(name)` (by name, so the rank you know; `IsUsableSpell` on an older client) while your target is an enemy that's alive. `Alert` when it turns usable (`usableNow[name]`, cleared by a new target or no enemy), but only once `usableLearned[name]`: the game has answered no without `insufficientPower`, which proves its answer depends on the target. Not enough rage or mana leaves the state as it was, so the alert comes when it can be pressed. A hidden answer is ignored. **Not yet seen in game**: that Forever's `IsSpellUsable` says no for Execute above 20% health.
- Lit-up spells (1.13.0): `SPELL_ACTIVATION_OVERLAY_SHOW` (a proc's overlay, its aura's spell ID: Clearcasting) and `SPELL_ACTIVATION_OVERLAY_GLOW_SHOW` (an action button lighting up) go to `OnSpellOverlay`: "<name>!" by `SpellName`. A glow within 0.2s of an overlay is the same proc and says nothing. `Alert(id, name)` is shared with `React`, with `REACT_GAP` per name, so Overpower from a dodge and from its glow shows once. Both events are in Blizzard_APIDocumentationGenerated for Forever with plain (not secret) payloads. **Not yet seen in game**: which spells Forever lights up.
- Combo points (1.13.0, `db.nCombo`, `TEXT_COLORS.combo`): `UNIT_POWER_UPDATE` for player with `"COMBO_POINTS"`. `ComboPoints()` reads `UnitPower("player", Enum.PowerType.ComboPoints)` (else `GetComboPoints("player", "target")`) and `UnitPowerMax` (else 5); both are `SecretWhenUnitPowerRestricted`, so a hidden value shows nothing. "N CP" when the count goes up, "N CP: Finish it!" (crit) at the most. `self.combo` is kept with the setting off, so turning it on doesn't repeat a count.
- Dispels (1.18.0, `db.nDispels`, on by default, `TEXT_COLORS.dispel`). From the log: `SPELL_DISPEL` / `SPELL_STOLEN` lines (Parse: `kind = "dispel"`, the spell link after the action is `extraSpell`/`extraSpellId`, what came off; `aura` is `"DEBUFF"` or `"BUFF"` from the action word, `ACTION_SPELL_DISPEL_DEBUFF` "cleansed" vs `_BUFF` "dispelled", left unset if a language words them the same; `SPELL_STOLEN` is always a buff and sets `stolen`). `ShowDispel`: yours or your pet's only; "Dispelled <aura>", "Purged <aura>" (a buff not on you), "Stole <aura>", with the aura's icon; a Spells-tab hide rule on the dispel spell hides it. The lines come only when the player ticks Combat Log → Settings → Message Types → Auras → **Dispels** (`COMBAT_CONFIG_MESSAGETYPES_LEFT` in ChatConfigFrame: one box for `SPELL_DISPEL`, `SPELL_STOLEN`, `SPELL_DISPEL_FAILED`; "My actions" has them off). Fallback: a cast (`OnSpellcast`) of a `DISPEL_SPELLS` spell (by ID or name; class cures, Purge, Tranquilizing Shot; not Abolish Poison/Disease, whose cast is a buff) waits `DISPEL_WAIT` (0.5s) and shows its own name if no dispel line of yours came (`dispelLineAt`). Once one has come since login, casts show nothing (the box is on, so no line = nothing came off). The Notifications page's Extras now share the Show card so the page fits `BODY_H`. In `/btf check` ("dispel"). **Not yet seen in game**: the lines arriving with the box ticked, Classic IDs on Forever, dispels from items, and whether Abolish Poison's later removals log as `SPELL_DISPEL`.
- Cooldowns ready (1.21.0, `db.nCooldowns`, on by default, `TEXT_COLORS.alert`, not crit). Forever's `C_Spell.GetSpellCooldown` is `SecretWhenCooldownsRestricted`, but its `isActive`, `isEnabled` and `isOnGCD` fields are `NeverSecret` (SpellSharedDocumentation, `SpellCooldownInfo`); `startTime` and `duration` can be hidden. `CooldownOf` reads it into `{ active, enabled, gcd, length }`. Your cast (`UNIT_SPELLCAST_SUCCEEDED` → `WatchCooldown`) goes in `self.cdCast` for `COOLDOWN_WATCH` (1s); `LookCooldowns` runs 0.1s after the cast and on `SPELL_UPDATE_COOLDOWN` (`update` true: the only time the docs say `isOnGCD` can be trusted). A cooldown of its own (`active` and `gcd == false`, or `gcd` unknown with a readable length over 2s) goes in `self.cooling` if its length is between `COOLDOWN_SHORTEST` (8s) and `COOLDOWN_LONGEST` (600s), or hidden. `enabled == false` is a held one (Stealth): it waits unseen until it's active, then the length check runs. Ready = seen active, now not active (or only the GCD left), and not held: `CooldownReady` shows "<icon><name> ready" (Spells-tab hide and color apply). While anything is cooling, `LookCooldowns` re-runs every `COOLDOWN_LOOK` (0.25s) with `C_Timer.After` (the game doesn't promise an event when one ends). **Not yet seen in game**: the NeverSecret fields really readable in a fight on Forever, and `isOnGCD` at the cast.
  - **1.21.6 (CurseForge: "Shoot ready" after every wand shot):** Shoot's cooldown is the wand's speed, `isOnGCD` false, and its `duration` is hidden in a fight, so the "hidden length is announced" rule let it through. `WatchCooldown` now skips `RepeatsOnItsOwn(id)`: every `RANGED_SPELLS` ID, or `C_Spell.IsAutoRepeatSpell(id)` true (plain bool on Forever, SpellDocumentation). Also, a cooling entry keeps `from` (the cast's time, or when a held one started) and `hidden` (length unreadable); a hidden one that ends less than `COOLDOWN_SHORTEST - COOLDOWN_SLACK` (7.5s) after `from` isn't announced. The test's Kidney Shot (hidden 20s) now runs its full length.
- Interrupts (1.21.0, `db.nInterrupts`, on by default, alert color, crit). `UNIT_SPELLCAST_INTERRUPTED` (registered for every unit) carries `interruptedBy` (a GUID; the event is `SecretWhenUnitSpellCastRestricted`). `OnInterrupted`: not you or your pet, an enemy (`UnitCanAttack`); a readable `interruptedBy` must be your GUID or your pet's ("(Pet) " in front). Hidden or empty: only your target, within `INTERRUPT_TIME` (0.5s) of your cast of one of `INTERRUPT_SPELLS` (`NoteInterruptCast` → `self.kick`; Pummel, Shield Bash, Kick, Earth Shock, Counterspell, Feral Charge, Silence, by English or local name). Shown once per `castGUID` (the event comes for each token the unit has; a hidden GUID shares one key) within 1s. Text: "Interrupted <spell>" with the stopped spell's icon, or "Interrupted!" when the spell ID is hidden. **Not yet seen in game**: whether `interruptedBy` is readable on Forever, and that a kicked mob's cast fires this event (not only `_STOP`/`_FAILED`).
- Low health and low mana warnings (1.25.0, `db.warnHealth`/`db.warnMana`, off by default, Incoming tab "Warnings" card; `TEXT_COLORS.lowHealth`/`lowMana`, crit; sounds `db.lowHealthSound` (RAID_WARNING) / `db.lowManaSound` (READY_CHECK), played by `PlayAlert`, `MAP_PING` fallback). Asked for on CurseForge (rroquette, to replace MSBT).
  - Health: Forever's `UnitHealth` is `SecretReturns` (always hidden from addons); `UnitHealthMax` is only secret for units that aren't player-controlled. So `HealthLow()` reads the numbers when they're readable (a test or a future client), else goes by the game's own red screen edges: `LowHealthFrame` (Blizzard_FrameXML Shared/LowHealthFrame.lua, Mainline xml) is shown by the game's secure code at `UnitHealth/UnitHealthMax <= 0.35` (`lowHealthPercentStart`). BattleText only reads `IsShown()` and `HookScript`s its OnShow/OnHide (no SetScript, nothing assigned). It also shows in a fight while a fullscreen panel is open (`GetUIPanel("fullscreen")`, the map) whatever your health, so that reads as "can't tell" (nil). With the game's "flash screen at low health" option off (`doNotFlashLowHealthWarning`) it never shows, so no health warning; the tooltip says so. Dead or ghost (`UnitIsDeadOrGhost`) counts as not low.
  - Mana: `UnitPower`/`UnitPowerMax("player", Enum.PowerType.Mana)` (`SecretWhenUnitPowerRestricted`: secret unless the power type is flagged never-secret). `ManaPercent()` is nil when hidden or `UnitPowerMax` is 0 (no mana). Checked on `UNIT_POWER_UPDATE` player `"MANA"`. Line `db.lowManaAt` (10-60%, default 35); re-arms only `MANA_BACK` (10) points above it, so regen ticks or drinking around the line don't repeat it.
  - **Hidden mana (1.28.0).** Player mana is secret for some players (issue #26's debug), so `ManaPercent()` is nil and no crossing can be timed: no "Low mana!" line, no sound. Instead `CheckLowMana` calls `UpdateManaSign(hidden)`: a steady "Low mana" (`self.manaSign`, FontString on its own frame, HIGH strata, crit size and outline, `TEXT_COLORS.lowMana`) anchored BOTTOM to the TOP of the Notify area (+6). Its frame alpha is `UnitPowerPercent("player", Mana, false, curve)` (SecretWhenUnitPowerRestricted + SecretWhenCurveSecret: a secret) passed straight to `SetAlpha` (SimpleFrame SetAlpha: `SecretArguments = "AllowedWhenTainted"`), never read back. `ManaSignCurve()`: `C_CurveUtil.CreateCurve`, `Enum.LuaCurveType.Step`, points (0, 1) and (lowManaAt/100 + 0.001, 0): step curves take a point's value from that point up, so the line itself counts as low, like the read path. Rebuilt when `lowManaAt` changes. Shown only while hidden, `warnMana`, `enabled`, `UnitPowerMax` mana > 0 (readable for the player: SecretWhenUnitPowerMaxRestricted is only for units that aren't player-controlled) and the API exists; dead = not hidden (pct 100). `ApplyAreas` (slider, switches, moving areas) re-runs `CheckLowMana` once the sign exists. No `MANA_BACK` hysteresis here (a stateless curve). Debug: `LOW MANA mana hidden: ...` when the sign is first made. Looked at and dropped: Blizzard_CombatText's `CombatText.lowMana` (secure code compares at a fixed 20%, only while the game's floating combat text is on, which "Hide Blizzard text" turns off); Blizzard_CombatAudioAlerts (text to speech, private state); `C_Spell.IsSpellUsable` insufficientPower (only says a spell's cost isn't met). **Not yet seen in game**: that `UnitPowerPercent` with a curve and a secret `SetAlpha` behave as the API docs say.
  - `CheckLowHealth`/`CheckLowMana` keep `self.healthLow`/`self.manaLow`; a warning only on false -> true, so the first look (`PLAYER_ENTERING_WORLD`, or the first event) only notes where you are. `Warn` skips the same warning within `WARN_GAP` (5s). `UNIT_HEALTH` is now registered for `target` and `player` (player goes to `CheckLowHealth`, target still to `CheckUsable`), plus `UNIT_MAXHEALTH` player.
  - **Not yet seen in game**: that `LowHealthFrame` shows/hides as the source says on Forever, and whether player mana is readable (in and out of a fight). To check mana: `/run print(issecretvalue(UnitPower("player",0)))` in and out of combat.
- Life Tap (1.27.0, issue #26: `/btf debug` showed only `CAST 1456 Life Tap`, no combat log line and no `UNIT_COMBAT player` ENERGIZE or WOUND). `LIFE_TAP` (1454, 1455, 1456, 11687, 11688, 11689; ranks from Classic, `/btf check` lists them as "health into mana") or its name (`IsLifeTap`, English or the game's name for 1454). `OnMana` (every `UNIT_POWER_UPDATE` "MANA") keeps `self.manaSeen` and notes a rise; `LifeTapCast` (from `OnSpellcast`) takes a rise in its own frame (within 0.01s, the update can come before the cast's event), otherwise the first rise within `LIFE_TAP_TIME` (0.5s) after it. `ShowLifeTap`: "-N Life Tap" (`InDamage`, `db.inDamage`) and "+N Mana Life Tap" (`InPower`, `db.inPower`, off by default). Player health is always secret, so the damage is the mana gained (1:1). When mana ended at its max (gain cut short) or nothing rose within 0.5s, the damage is the first number in `C_Spell.GetSpellDescription` if bigger; no number, no line. Hidden mana (`UnitPower` is `SecretWhenUnitPowerRestricted`): nothing. If the game ever sends its own energize (log or `UNIT_COMBAT`) while a tap waits, `LifeTapLogged` drops our mana line. A spell rule hiding Life Tap hides both. Known limits: a talent that adds mana (Classic's Improved Life Tap) makes the damage shown too high by that bonus; a regen tick landing inside the 0.5s before the tap's mana would be taken as the tap's. **Not yet seen in game**: that `UNIT_POWER_UPDATE` fires in or right after the cast's frame, and the description's wording on Forever.
  - **1.27.1 (mtfic on issue #26: "-N Life Tap" showed, "+N Mana" never did, Power gains on, mana not full).** The health came from the description fallback, so no rise was seen in the window. Likely the server's mana arrived a frame or more before `UNIT_SPELLCAST_SUCCEEDED` (1.27.0 only took a rise within 0.01s before) or later than 0.5s. Now: a rise up to `LIFE_TAP_BEFORE` (0.3s) before the cast, or up to `LIFE_TAP_TIME` (1.5s) after; `UNIT_POWER_FREQUENT` (player) also calls `OnMana`; and `LifeTapCast` reads the bar at the cast (`tap.before`) and looks again every `LIFE_TAP_LOOK` (0.1s), taking the first reading above it. Debug lines: `LIFE TAP mana N/MAX (rose X Ys before)` at the cast, `MANA a -> b` near a tap, `LIFE TAP <how>: mana N` when shown (how = before, mana event, mana bar, no mana). A regen tick inside the window is still taken as the tap's. **Not yet seen in game.**
  - **1.27.2 (mtfic's 1.27.1 debug: `LIFE TAP mana hidden` then `LIFE TAP no mana: mana nil (full)` on every cast, mana not full).** Player mana (`UnitPower("player", 0)`) is secret for them, so no rise can ever be read. With the mana hidden at the cast (and no readable rise just before), `LifeTapCast` sets `tap.hidden` and shows at once: `LifeTapAmounts(id)` takes the first two numbers of `C_Spell.GetSpellDescription` (color codes stripped; one number = both) as health and mana. No description: nothing. Readable mana keeps the 1.27.1 path. Known limits: with hidden mana a tap at full mana still shows "+N Mana"; Improved Life Tap only shows if the game's description includes it. This also means the low mana warning (`ManaPercent`) can't work while the mana is hidden.
- Smallest crit (1.21.0, `db.minCrit`, 0 = off, Text tab, range 0..1000). `BigCrit(crit, n)`: a readable amount under it isn't a crit. `Emit` clears `opts.crit` with it (so the line is normal size and outline, doesn't hold, and can merge), and the crit sound in `ShowCombat` and `ShowUnitHit` asks it too. A hidden amount stays a crit; notifications with `crit` have no amount and are untouched. `CountSpell` still counts it as a crit for `/btf last`.
- Spell rules (1.13.0, Spells tab, `db.spellRules`: a list of `{ name, hide, color }`, a list so names with spaces export). `SpellRule(name)` looks one up by lower-case name (`rulesByName`, rebuilt after `AddSpellRule`, `RemoveSpellRule`, `SetSpellRule` and in `ApplySettings`). Used for your hits, misses and heals (and your pet's): in `ShowCombat` by the line's spell, in `ShowUnitHit` by the name it worked out. Hidden lines still count in the fight. `ReadSettings` takes only entries with a name of 1 to 60 letters, a color of three numbers kept to 0..1, and `hide` only when it's `true`.
- Last fight (1.13.0, `/btf last`, `OpenLastFight` in Options.lua): `CountSpell(name, n, crit, heal, icon)` beside each `CountFight`, into `self.fight.spells` (by kind and name; "(Pet) " in front of your pet's, "Auto attack" or "Unnamed <school>" for hits nothing named). `FightSummary` keeps a fight with anything in it as `self.lastFight` (with `secs`), whether or not the summary is on. `FightBreakdown` sorts damage first, then heals, biggest total first, with `share` (percent of its kind). The window is a `Popup` (the header the copy window has too) with one row of font strings per spell.
- Dropdowns never use the game's menus (1.14.0, issue #9). `T.Dropdown` opened `MenuUtil.CreateContextMenu` until 1.13.0; the game's menu system is shared with its unit menus, and after an addon opened a menu, picking a raid marker from a unit frame's right-click menu was blocked (`SetRaidTarget` has `HasRestrictions` on Forever, `RaidMarkersDocumentation.lua`) and blamed on BattleText. Now `T.OpenList(owner, items, scroll, title)` shows `T.List()`, one frame of our own (`<Addon>DropdownList`, in `UISpecialFrames`) over a full-screen `catcher` button that closes it on any other click; it also closes when the owner stops being visible (`OnUpdate`). `scroll` (the dropdown's `menuScroll`) is a height: rows of 20, mouse wheel by 3. The stub's `MenuUtil.CreateContextMenu` records a violation, so any use fails the tests. Theme.lua changed: copy it to the other three addons.
- Swing icons (1.14.0, issue #8): `SwingIcon()` is the main hand's `GetInventoryItemTexture("player", 16)`, else spell 6603's icon (Attack). `UNIT_COMBAT` can't tell main hand from off hand. Used in `ShowUnitHit` for a hit nothing named that's physical or a plain miss (what `outSwings` hides), and in `ShowCombat` for a readable `info.melee` line of yours. **1.21.3 (issue #15: a rogue's off-hand hits still showed the main-hand sword):** 1.16.0's dual-wield check read the off hand's speed from `UnitAttackSpeed`, which is `SecretWhenUnitStatsRestricted` on Forever (Gethe `UnitDocumentation`), so `Num()` gave nil and it fell through to the main hand's icon. Now `OnSwing` also keeps `self.hands` (`{ at, hand }`, swingType 0 main / 1 off; ranged 2 isn't kept; within `CREDIT_TIME`, at most 6) and sets `self.dualWield` on an off-hand swing (cleared by `PLAYER_EQUIPMENT_CHANGED` for slot 16 or 17). In `ShowUnitHit` a swing (unnamed physical hit or miss) asks `SwingHand(h)`: the oldest kept swing at or before the hit, on your target only (same test as `ClaimSwing`), taken off the list. `SwingIcon(hand)`: 1 is slot 17's texture, 0 slot 16's; unknown is the Attack icon with `dualWield` or a readable off-hand speed, else the main hand's. ## Where the combat data comes from

Forever refuses `COMBAT_LOG_EVENT` and `COMBAT_LOG_EVENT_UNFILTERED` to addons. What's left:

- **`UNIT_COMBAT`** — what happened to a unit: `unit, action, flag, amount, schoolMask`. No source, no spell. This is the one that always works, and since 1.1.0 it's the main source (next section).
- **`COMBAT_LOG_MESSAGE`** — the finished text of each Combat Log window line. The game **hides the text** (below), so mostly it only says *that* you did something.

### The lines are hidden (since 2026-10-03)

On 2026-10-02 the lines arrived as readable text and 1.0.0 was built on parsing them. On 2026-10-03 (client 1.60.1.70205) every live line arrived as a **`|Ky<n>|k` token** (`|Ky7|k`, `|Ky8|k`, ...): a "K-string", which a font string can display but an addon can't read, split or measure. Blizzard's API notes have said so all along (`CombatLogSecureDocumentation.lua`: "A preformatted combat log message protected by a |K string wrapper"); none of the game's Lua changed between the builds, so the switch is in the client or on the server. Other Forever addons report the same and say lines can still be readable at times (out of combat), so **both paths are kept**: a readable line is parsed as before, a hidden one is only counted.

### Hits from `UNIT_COMBAT` (`OnUnitHit`)

Registered for every unit (`RegisterEvent`, not `RegisterUnitEvent`). `"player"` goes to `OnUnitCombat` as before (what happens to you); every other unit token goes to `OnUnitHit`, which decides whether it's something you did:

- **You and your pet under other names** (`targettarget`, `raid3`, `focus`...) are dropped: `"player"` has its own event, and of what happens to your pet only heals on the `"pet"` token are shown (as your heal).
- **Damage and misses** need a unit you can attack (`UnitCanAttack`) that you're **fighting**: your target, your pet's target, or a unit whose target is you or your pet (`Fighting`). So a mob someone else is fighting nearby isn't yours. Except **area damage** (since 1.7.1, reported with Fire Nova): damage on an enemy you're not fighting is queued as `splash`, and `ResolveFrame` shows it only if a hit of yours (`h.mine`: shown, damage) of the same school landed in the same frame on one you are fighting; it's named as that hit was. In a group it still needs its own line (`ClaimHit`). Misses on such mobs aren't shown. Units other than your target only have a token when their **nameplate** is showing.
- **Heals** need a friendly unit: alone, your target; vouched for (below), any friendly unit.
- **One hit, many names.** The event fires once per token the unit has (`target`, `nameplate3`, `focus`). `FirstSight` keeps, per frame and per GUID, only the first token seen, so duplicates go and two real hits in one frame stay. With no readable GUID, your target counts under `target` only.
- **A readable line of yours** (or your pet's) in the last 1.2s (`readAt`) means the log is showing your hits itself: the unit's hits are dropped so nothing is doubled.
- **Alone**, before any line has arrived (Start not clicked), everything that passes is shown. Your pet's hits can't be told from yours.
- **Alone with the lines** (1.18.4, a CurseForge comment: other players' damage on your target showed as yours): `OnUnitHit` sets `grouped` ("needs vouching") when `hiddenSeen` and either `InGroup()` or not `PetOn(unit)`; `solo` marks the alone case. `PetOn`: you have a pet and the unit is `pettarget` or its target is the pet. Its hits have no line under "My actions", so on a unit the pet is on, alone, hits stay unvouched (shown as before). In `ResolveFrame`, a `solo` hit that's a damage shield's (`what == "shield"`) or may be one (`ShieldOn`, held by `WaitForSwing`) counts as claimed: `DAMAGE_SHIELD` isn't in "My actions" either. In a group they're still dropped without a line (unchanged). The real-fight replays from before `PLAYER_SWING` was recorded (`real_fight.txt` to `real_fight4.txt`) now get a synthetic `PLAYER_SWING` before each physical hit on the target (once per hit, not per token), as the game would send. **Not yet seen in game**: alone, white hits all vouched by `PLAYER_SWING` (only confirmed indirectly, from the group fix of 1.16.3), and hunters/warlocks whose pet is on a different mob than the one they hit.
- **Swings** (1.16.3, issues #15, #16): the "My actions" lines don't come for every swing (players' `/btf debug`: a rogue's 9 swings in 7s had 6 lines; a warrior's misses had none), so in a group many white hits and the mob's dodges of them were "no line of yours with it". `PLAYER_SWING` (Forever's swing timer, `SwingTimerDocumentation`: `swingDuration`, `swingType` 0 main / 1 off / 2 ranged, plain values) is registered: `OnSwing` keeps one credit per swing (`self.swings`, `CREDIT_TIME`); `ClaimSwing` gives one to a physical hit or a miss on your **target** (auto attacks only go at your target), before line credits are tried. A hit named as the frame's cast (`what == "cast"`) is claimed by the cast itself (using up a line credit if there is one): a miss has no line under "My actions". **Not yet seen in game**: when `PLAYER_SWING` fires against the hit's `UNIT_COMBAT` (assumed before it or in its frame).
- **In a group**, once a hidden line has been seen (`hiddenSeen`), a hit must be **vouched for** (`ClaimHit`): with the "My actions" filter every line is an action of yours, so each hidden line is one credit (`NoteHiddenLine`), good for 1.2s (`CREDIT_TIME`) and for one hit. Hits are worked out when their frame is over, so a line that arrives just behind its hit still counts. Imperfect by nature: a groupmate's hit landing between your line and your hit takes the credit (and shows their number instead of yours). In a group before any line has arrived (Start not clicked), every hit on a unit you're fighting is shown.
- **Lines vouch for their own hit** (1.21.4, issue #16 follow-up: a protection warrior's party member's wand hits (school 64/32) and white hits on the target showed as theirs). In the reporter's `/btf debug`, Sunder Armor and Shield Block each send a line in their cast frame with no hit, and since 1.16.3 a swing is vouched by `PLAYER_SWING` (`ClaimSwing`) while its line (0.2–1.2s ahead of the hit) was left in `self.credits` too: any hit within `CREDIT_TIME` took those. `ClaimHit(now, h)` now takes a credit within `LINE_WITH_HIT` (0.15s) at or before the hit (spells, ticks, procs, heals come with their line; real_fight5's Shadow Bolt line came 0.11s ahead), oldest first; an older one only when `WideClaim(h)`: a physical hit or miss, and not on your target while you've swung lately (`self.swungAt`, set by `OnSwing`, within `SWING_RECENT` 6s) unless your pet is on it (`PetOn`: its swings' lines come ahead too, with Pet ticked under "Done By"). Casts and splash hits go through the same rule. **Still open**: a party member's white hit on your target landing between your `PLAYER_SWING` and your own hit takes your swing's credit (then yours is the one dropped); the timing of `PLAYER_SWING` against the hit's `UNIT_COMBAT` for melee hasn't been recorded yet (a `/btf debug` with `SWING 0` lines in a group would show it). Party white hits on a mob that isn't your target but is after you can still take an earlier line.
  - **1.21.6 (CurseForge: wand damage not showing consistently):** a wand hit's own "My actions" line can come a frame after its `UNIT_COMBAT`, and then the hit had no line within `LINE_WITH_HIT` ("no line of yours with it"). `ClaimFlight(h)` (after `ClaimSwing`/`ClaimHit`): a hit `FlightFor` gives to an `auto` flight (`RANGED_SPELLS`) is yours if a credit (line) arrived between that flight's cast and the hit (the shot's cast line), which is used up. Spells that fly (Fireball) still need a line in their frame (someone's Fire hit while your Fireball flies isn't yours: test kept). With "Pet" lines and solo without a pet, `grouped` is true too, so this affected solo players as well.
- **Extra attacks** (1.28.2, GitHub #27: a shaman's Windfury Weapon hits never showed; `/btf debug` had a Stormstrike at 112.26 with three lines in its frame, then two physical crits on the target at +0.22s and +0.50s marked "no line of yours with it"). Extra attacks fire no `PLAYER_SWING` and have no line in their own frame; `ClaimHit` only lets a physical hit take an earlier line when no swing is recent (`WideClaim`), so they were refused, alone too (`h.grouped` is set alone once the lines flow; `h.solo` then). Not caused by 1.28.1 (that only touched `EveryHitFor`). Fix: a claimed landed physical blow that was a plain hit or a cast (Stormstrike) calls `OpenExtra(h)`: `self.extra = { key, at, left = EXTRA_HITS (2) }` (not opened by a hit that was itself an extra). `ClaimExtra(h)`, tried after `ClaimSwing`/`ClaimHit`/`ClaimFlight`: a damage or miss of school 1 on the same unit key, 0 < time since blow <= `EXTRA_TIME` (0.8). Alone that's enough; in a group (`not h.solo`) it must also remove a credit whose time is exactly the blow's frame (the proc's spare lines), so a party member's white hit after your swing (whose line came with `PLAYER_SWING`, earlier) or after Sunder's line in a later frame isn't taken. Works for any extra attack (Hand of Justice, Sword Specialization, Windfury Totem), named like a white hit. Tests: "GitHub #27" in run_tests.lua; mutations (no `ClaimExtra`; no group credit check; extra reopening the window) each fail a test. **Not yet seen in game.**
- Amount, crit (`flag == "CRITICAL"`) and school (`schoolMask`: 1 physical, 2 holy, 4 fire, 8 nature, 16 frost, 32 shadow, 64 arcane) come from the event. `GLANCING`, `BLOCK_REDUCED`, `ABSORB`, `RESIST` flags on a hit add a note. A `WOUND` for 0 is a miss (the flag says how), as for the player. A hidden (secret) amount is handed to the game to draw (`Emit`'s `opts.secret`).

### Which spell it was (`ResolveFrame`)

A hit that passes isn't shown at once. Everything in a frame (hidden lines, your casts, hits) goes into `self.seq` in the order it came (`Queue`), and a zero-delay timer works the frame out when it's over (`FlushHits` → `ResolveFrame`), because what comes before and after a hit says what it was. Tests look through `lines()`/`last()`, which flush first.

What a real fight looks like (`tests/real_fight.txt`, a cat druid with Thorns, 2026-10-03), and the rules read off it:

- **An instant attack**: `hidden, CAST, hidden, hit`, all in one frame. Rule: **exactly one cast in the frame names its hits** (`UNIT_SPELLCAST_SUCCEEDED` for the player, `OnSpellcast`). Not for a spell that only ticks (`direct` false in the table: Rip's cast names no damage, though it names its own miss), and not for a hit of another school than the cast's first hit, or than the school the spell was seen to have before (`spellSchool`): Thorns answered in the very frame of an opening Claw.
- **A swing**: its line, then the hit 0.2–1.2s later (with the animation), usually with no line in the hit's frame. In cat form (a swing a second) a swing's hit sometimes lands in the frame of the *next* swing's line: then the order is `hidden, hit`.
- **A tick**: `hit, hidden` in one frame, the line right behind the hit (10 of 10). Rule (`TickFor`): the hit's unit has a damage-over-time spell of yours on it (remembered from the cast, against your target then: `self.dots[key][name]`, forgotten after 45s or when the cast's own frame holds a miss), the hit is on its beat (a whole number of periods since the cast, or since its last named tick (`dot.last`, 1.17.1), give or take 0.25s; the recording's ticks were within 0.09s; a hit less than half a period after its last tick is never another tick of it), of its school, and **a line comes after the hit in the frame** (each line vouches for one tick). With no lines arriving at all (Start not clicked), a tick is named on beat and school alone, and only if it isn't physical: a bleed's tick would be a coin toss against a swing.
- **A damage shield**: a hit with no line (`DAMAGE_SHIELD` isn't in the "My actions" filter), followed 0.3–1.0s later by `UNIT_COMBAT player WOUND` (the blow it answered, shown with its animation). There can be several at once: in `tests/real_fight2.txt` every blow is answered by 11 Nature (Thorns) and 1 Nature (a cape, "Equip: When struck in combat, inflicts 1 Nature damage to the attacker"), in the same frame. (The 1s in the first recording were the cape too; 1.2.0 took them for Thorns.)
  - **Gear** (`ScanItemShields`, `self.itemShields`): each equipped item's tooltip (`C_TooltipInfo.GetInventoryItem`) is searched for "inflicts N School damage to the attacker". English only. That gives the amount, school, name and icon outright; a hit of that school and amount is the item's. Read when gear changes, on entering the world, and as a fight starts and ends (never in one).
  - **Buffs** (`ScanShield`, `self.buffShields` by name): your buffs are read on `UNIT_AURA`, entering the world and as a fight starts and ends; they're hidden in a fight, so the last answer stands, and casting one adds it. A buff's amount isn't known, so it's **learned** (`ShieldFor` → `ConfirmShield` → `LearnShield`): a hit of the buff's school that nothing else explains waits up to 1.2s for a blow on you. While the hidden lines are arriving, only a hit from a frame with no line in it counts (a spell of yours landing has its line). An amount that has answered two blows is given to the buff whose description names it (`C_Spell.GetSpellDescription`, whole numbers), or to the only buff it could be when it's the only amount needing an owner; it takes three answers to replace an amount learned before. Kept in `db.shieldAmounts[name]`. The amount test is what keeps a druid's Wrath from being taken for Thorns.
  - A known shield's hit (`KnownShield`) is the shield's even in the frame of a cast, unless the cast is of that school too.
- **A hit on you for nothing** (`UNIT_COMBAT player WOUND` with amount 0 and no flag) is a miss only on its own. Some mobs' special attacks arrive as `WOUND 0` and `WOUND 33` in one frame (`tests/real_fight3.txt`, three times, each a blow about twice a normal one): the empty part is queued (`nothing`) and dropped when a blow landed in the same frame (`blow`). A zero with a flag (`ABSORB`, `BLOCK`, `RESIST`) is its own attack and shows at once.
- **Which hit is the cast's** (`byLine` in `ResolveFrame`, since 1.2.3): the hit with a line of its own just ahead of it in the frame, on either side of the cast. Claw and Rake arrive as `CAST, line, hit`; Shred arrives as `line, hit, CAST` (`tests/real_fight4.txt`, and until 1.2.3 its hits went unnamed because the rule was "after the cast"). Each line vouches for one hit, the closest unused one before the hit; a shield's answer has no line and a tick's line comes behind it (a hit `TickFor` recognises keeps the line after it). The school and known-shield checks still apply. This only runs while lines are arriving (`linesFlow`) and the frame has exactly one cast.
- **Order in the frame** is the fallback when no hit in the cast's frame has a line (or no lines are arriving): a cast's hit comes after the cast, and a hit ahead of it is something else (the cape answered a blow just before a Claw landed).
- The periods and schools are in `PERIODIC_SPELLS` and `SHIELD_SPELLS` (first rank's ID, English name, ...), turned into name lookups by `SpellLists`: the English name always, the ID's name too on other languages. On an English client an ID whose name disagrees is ignored (Forever isn't quite Classic: its level 14 druid has Rake and Rip). The values are Classic's. **Checked in game with `/btf check` (1.8.0)**: every ID in `PERIODIC_SPELLS`, `SHIELD_SPELLS`, `SEAL_SPELLS`, `SELF_BUFFS` and `SKILL_SPELLS` exists on Forever under the name listed, after three fixes in 1.8.1: Forever names 980 "Bane of Agony" (the later name, not Curse of Agony), 12292 is Sweeping Strikes, and 16166 (Elemental Mastery) doesn't exist. The periods and schools are still Classic's: only Claw, Rake, Rip and Thorns are confirmed in a fight.
- `/btf debug` writes each event as it arrives, and then, indented, what each hit was taken for: `  nameplate2 28: tick of Rake`.

- **A spell that flies** (since 1.11.0, `FLIGHT_SPELLS`: first rank's ID, English name, school, and the period of the burn it leaves, for Fireball and Pyroblast): its cast frame has no hit; the hit comes in a later frame. `OnSpellcast` puts it in `self.flying` (oldest first, at most 10) against your target's key. In `ResolveFrame` a hit nothing else named (not the frame's cast) goes to `FlightFor`: the oldest flight cast at that unit, before this frame and within `FLIGHT_TIME` (2.5s, about 40 yards at a Shadow Bolt's speed), of the hit's school; a miss counts if it's of the spell's school or `SPELL_MISSES` (resist, immune, reflect: no swing misses that way). `Landed` takes it off the list and, for a burn, starts a dot at the hit's time (`self.dots`, as a cast does for the others). Guards, each with its test:
  - a tick of yours on its beat (`TickFor`) wins, unless its amount differs from what that dot has ticked for (`dot.tick`, set on every named tick): Insect Swarm while a Wrath is on its way;
  - against a flight (or a throw), `TickFor(h, true)`: a dot that has ticked (`dot.last`) must be within `TICK_CLOSE` (0.15s) of its beat, not `TICK_SLACK`. ### The readable lines (when the game allows)

1. **`COMBAT_LOG_MESSAGE`** — the finished text of each Combat Log window line: `message, r, g, b, order`. Blizzard's secure `Blizzard_CombatLogProcessor` builds it (`GenerateMessage`) for Blizzard's own Combat Log window; addons can register it too. On screen a line reads

       Your Claw hit Bristleback Hunter Faust 50 Physical. (Critical)

   and underneath every part is a link:

       |Hunit:<guid>:<name>|hYour|h |Hspell:16827:0:SPELL_DAMAGE|h|cffffffffClaw|r|h |Haction:SPELL_DAMAGE|hhit|h |Hunit:<guid>:<name>|hBristleback Hunter Faust|h |cffffffff50|r |cffffffffPhysical|r. (Critical)

   - The **action link** names the event (`SWING_DAMAGE`, `SPELL_MISSED`, `SPELL_HEAL`, `PARTY_KILL`, ...). The **spell link** has the spell's ID. A swing has no spell: its name ("Melee") is a second action link. The **unit links** before and after the action are who did it and who it happened to; yours read "You" / "Your".
   - **Names are scrambled.** The other unit's name changes from line to line (a random mob name and surname). Never use it.
   - `order == Enum.CombatLogMessageOrder.Oldest` is history replayed when the window refills (the game does this at login too). Skip it.
2. **`UNIT_COMBAT`** for `player` — damage, heals, avoids and power gains that happen to you, with no spell name. Needs no setup. `WOUND` with no amount is an attack that did nothing (`flag` says `ABSORB`, `BLOCK` or `RESIST`, else it's a miss).

### What makes the lines flow

- The game only produces them **after the Combat Log window has been shown** once since login or `/reload` (confirmed in game, 2026-10-02). That's when Blizzard's UI loads its filter with `C_CombatLog.ApplyFilterSettings` (in `COMBATLOG`'s `OnShow`).
- **Never call `C_CombatLog.ApplyFilterSettings`.** It's Blizzard-only: from an addon it's blocked ("action only available to the Blizzard UI"), and the half-applied filter then makes Blizzard's processor throw `bad argument #1 to 'sub'` on every combat event until `/reload` (confirmed in game).
- When the window hides, Blizzard calls `C_CombatLog.SetFilteredEventsEnabled(false)` and the lines stop. **An addon may call `SetFilteredEventsEnabled(true)`**, and the lines come back (confirmed in game). `KeepLogFlowing` does that on the window's `OnHide`, after the Start click, and on a 3-second ticker.
- **Starting by itself (1.23.0).** Blizzard's Combat Log code loads the filter when it loads at login (as Blizzard code, so the call is allowed), then turns the lines off because its window is hidden. `KeepLogFlowing` at `PLAYER_ENTERING_WORLD`, at `PLAYER_REGEN_DISABLED` and on the 3-second ticker (now always, not only once `started`) turns them back on, and lines arrive with no click (confirmed in game 2026-11-18: login, no click, `/run C_CombatLog.SetFilteredEventsEnabled(true)`, hit a mob, the button went at the end of the fight). The 2026-10-02 finding that a click is needed was made before `SetFilteredEventsEnabled` was known. Zore's Scrolling Battle Text works the same way (no button). This reverses the review's BT-026 note: the game now formats lines all session from login.
- With Chattynator installed it starts by itself too (confirmed in game 2026-11-18: no button, no chat warning after a fight).
- **Not yet confirmed in game:** that the filter loaded at login is the selected one (**My actions**), so other players' hits are left out in a group with no click. If not, the click is still needed for that.
- The **Start button** is now a fallback: hidden until a fight ends with no line (`CheckAutoStart` at `PLAYER_REGEN_ENABLED` sets `startNeeded`). It's a secure button whose macro is `/click ChatFrame2Tab` then `/click <the tab you were on>` (or, if you're on the Combat Log tab, `/click ChatFrame1Tab` then `/click ChatFrame2Tab`): Blizzard's own code opens and closes the window, untainted. `ChatFrame2:Show()` from addon code would run that `OnShow` tainted and hit the blocked call. It's registered for `AnyUp` and `AnyDown` because the game runs a macro button on one or the other (the `ActionButtonUseKeyDown` setting).
- **Starting from the player's own macro** (1.22.0): `/click BattleTextForeverStart` in a macro they press anyway. Forever's `/click` (`SlashCommands.lua`) calls `button:Click(mouseButton, down)` with `down` false unless a third word says otherwise, so only the release arrives; with `ActionButtonUseKeyDown` on (the default) `SecureActionButton_OnClick` would skip it. The button sets `useOnKeyDown` to false, so mouse, key binding and `/click` all act on the release. Once `started`, `SetStartMacro` clears `type` and `macrotext`, so later presses do nothing (it runs on `PreClick` and at `PLAYER_REGEN_DISABLED`, out of combat). If the lines start in the middle of a fight, the macro can't be cleared until it ends, so each press in that fight still opens and closes the Combat Log tab (harmless). The test stub's `ClickButton(b, which, true)` sends the release only, like `/click`.
- **The reminder** (`RemindStart`, since 1.2.4; since 1.23.0 from `CheckAutoStart`, once a session, when the button first shows): one chat line if `started` isn't set, naming the key bound to `CLICK BattleTextForeverStart:LeftButton` if there is one. Off with `db.startReminder` ("Remind me to click Start") or when BattleText is off.
- **The login line** ("BattleText Forever loaded. Type /btf for options.", `PLAYER_LOGIN`) shows only with `db.loginMessage` (1.18.0, General tab, on by default, not shared in exports). Both chat lines are login and `/reload` only, never a loading screen.
- The button hides once the Combat Log window has been shown (its `OnShow`), or a live line has arrived (`started`). The macro can only be changed out of combat, so it's refreshed on each click, when a fight starts and when one ends.
- Not handled: a Combat Log dragged out into its own window (its tab's click doesn't show or hide it). Clicking a filter's quick button on that window would be the way (`Blizzard_CombatLog_QuickButton_OnClick` loads the filter), untested.
- `/btf off` puts the lines back the way the game has them (off unless its window is showing).

### What the lines contain

They follow the **filter selected on the Combat Log tab** (`Blizzard_CombatLog_Filter_Defaults` in `Blizzard_CombatLog.lua`):

- **"My actions"** (the default): you as the source, and only these events: swing, ranged, spell and periodic damage, heals and periodic heals, `DAMAGE_SPLIT`, `PARTY_KILL`, `UNIT_DESTROYED`, `UNIT_DISSIPATES`. **No misses, no power gains, and not your pet.** The player can add misses and the pet: with "My actions" selected on the tab, right-click the Combat Log tab → Settings → Message Types (four Misses boxes: melee, ranged, spells, periodic) and Message Sources (Pet under "Done By"; the one under "Done To" only adds hits on the pet) → Okay. Power gains have no box there; they come from `UNIT_COMBAT`.
- **"What happened to me?"**: you as the target (damage and heals, no misses).
- A filter the player makes themselves can have both.

`ShowCombat` takes whatever arrives:

- Your pet's lines are told apart by the source link's GUID (`UnitGUID("pet")`).
- What happens to you normally comes from `UNIT_COMBAT`. When the log starts delivering it (`NoteLogIncoming`, per kind: damage, miss, heal, power), `UNIT_COMBAT` is ignored for that kind so nothing is doubled; three `UNIT_COMBAT` events with nothing from the log switch it back (`LogCovers`).
- Your own heals on yourself arrive both ways. `UNIT_COMBAT` heals wait 0.25s and are dropped if the log had one of the same amount in the last 0.6s (`NoteSelfHeal`, `TakeSelfHeal`; a hidden amount matches any). Since 1.7.2 only that one heal is dropped: before, any heal in that window was, so another player's heal at the same moment went missing. Damage you do to yourself is left to `UNIT_COMBAT`.

### Reading the lines (`Parse.lua`)

- **Links first** (`ParseLinks`): the event comes from the action link, so nothing depends on the game's language. The number and the notes after it ("(Critical)", "(3 Blocked)", "(Dodged)") are matched against the game's own global strings (`TEXT_MODE_A_STRING_RESULT_*`, `ACTION_*_MISSED_*`).
- **Words as a fallback** (`ParseWords`), for a line with no links: finds "Your" and the action word (`ACTION_<EVENT>` strings). Someone else's line can't give a spell name this way (their scrambled name runs into it).
- A spell that fails says how in place of the action word ("Your Moonfire resisted X."); a swing says it in a note ("Your Melee missed X. (Dodged)").
- With the Combat Log's "Use Verbose Mode" the sentences are different and have no action link. Not supported.
- `/btf debug` records every live line exactly as the game sent it, marked "read", "skipped" or "hidden", each `UNIT_COMBAT` with its unit and (for other units) whether it was shown or why not, each cast of yours (`CAST <id> <name>`), and the time each arrived (the last 300). `/btf copy` shows them in an edit box (with `|` doubled so the links can be read), because chat can't be copied.

## WoW Forever rules the code must follow

- **Lua 5.1.**
- **Secret values.** Some API results are hidden from addons; comparing or doing math on one throws, **even `v == nil`**. Check `IsSecret(v)` first, or use `Num()` / `Str()`. A secret can still go to `SetText` / `SetFormattedText` (`Emit`'s `opts.secret`).
- **`tostring` of a secret is a secret string** (1.21.5, issue #23). Joining or formatting it makes the whole text secret, and `table.concat` refuses it. `WaitForGrave`, `WaitForSwing` and `Resolved` recorded `tostring(h.amount)` in the debug log, so `/btf copy` (`OpenCopyWindow`) failed with "invalid value (secret) at index N in table for 'concat'" after a Touch of the Grave wait ran out. Debug lines use `AmountText(v)` ("(hidden amount)"); `Record` keeps only `Str(text)` (else "(a line with a hidden value)") and `OpenCopyWindow` does the same per line. The stub's `__tostring` on a secret now returns a secret, so `format("%s", ...)` and `table.concat` fail in the tests as in the game.
- **Taint.** Never assign one of Blizzard's globals or `SetScript` on Blizzard's frames (`HookScript` is fine).
- **Combat lockdown.** The Start button is secure: creating it, its attributes, and showing or hiding it wait for combat to end (`startPending`). The text areas and lines are ordinary frames and can change in combat.
- **Hardware events.** Nothing here sends chat or does protected actions. The Start button's macro runs from the player's click.

## Releasing

1. Make the change, run the tests, and add a new section at the top of `CHANGELOG.md` (e.g. `## 1.0.1`).
   If the change shows on the CurseForge project page (features, options, commands), update `CURSEFORGE.md` too (the README, adjusted: no logo, a short install note, full links) and give the whole file to paste into the project's description. The packager only uploads `CHANGELOG.md` with each file; the description never changes on its own.
2. Commit and push to `main`. The **Tests** workflow must be green.
3. Create the tag in GitHub Desktop (History tab → right-click the commit → Create Tag → e.g. `v1.0.1` → Push origin). Tags containing `beta` or `alpha` upload as Beta/Alpha files.
4. The **Package and release** workflow runs the tests again, then uploads to CurseForge. Check the Actions tab for a green check and the CurseForge Files page (new files go through CurseForge review).
